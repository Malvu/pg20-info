Read this first

This setup opens ports to the Internet and gives permanent access to clients' computers. Go ahead only if you know how to maintain an exposed server, and only with each client's written agreement.

Levels 1 and 2 expose RustDesk only. Level 3 also exposes a small service written for this project, and installs a maintenance task on each client computer: these are the elements that add a risk of their own. You can stop at level 2.

What it does

The goal: install RustDesk at a client's, then connect to it later without retyping an ID or a password. Here is one installation, from the technician's point of view on site.

  1. The client double-clicks the exe (USB key or link). Windows asks for administrator rights.
  2. The client reads and accepts the terms: a window shows the text, the client ticks the box and types a name. Without acceptance, nothing is installed. The acceptance (name, date, fingerprint of the text) is kept as proof.
  3. The exe installs RustDesk, configures it for your server with its key, and sets a permanent password of at least 12 characters, typed or generated. It also installs a small maintenance task, which can only uninstall RustDesk on an order signed by you.
  4. The exe sends an encrypted record (name, ID, password) to your server. The server cannot read it. It picks a 4-digit code, which the exe displays at the client's.
  5. Your phone rings: name, ID and code. You compare with the client's screen, then tap Validate. The window at the client's then shows "Validated" and closes by itself.
  6. Your PC fetches the record, decrypts it with a private key that never leaves your PC, and applies the validation.
  7. A desktop icon "Connect" lists the validated clients. One click opens RustDesk with the ID and password already filled in.

The same address book lets you uninstall RustDesk at a client's with one click (the computer uninstalls itself, within half an hour, with nothing for the client to do) and delete a client everywhere in one gesture: PC, USB key and server.

What it does not do
  • No "online" status for clients: the RustDesk server does not expose it.
  • Windows clients only (the exe). A macOS or Linux computer is configured by hand with the same options.
  • A single technician: the private key lives on one PC (plus a backup).
  • No code signing: Windows and some antivirus programs may distrust the exe.
  • No hidden remote control: the maintenance task installed at the client's can only uninstall RustDesk, and only on an order signed by your key. It is described to the client in the terms they accept.

The three levels

Build them in order and let each level run for a few days before moving to the next. The project is about 4,700 lines written for the occasion (PowerShell, C#, Python, HTML), split as follows.

What you need

  • A machine for the server: a Debian 12 VM with 1 vCPU, 1 GB of RAM and 16 GB of disk is enough. Proxmox is not required, any Linux with Docker will do.
  • Access to your router to forward ports, and a stable public address (fixed IP or DDNS name).
  • A Windows 10 or 11 PC for the technician. PowerShell 5.1 and the C# compiler shipped with Windows are enough, nothing to install.
  • For level 3: Home Assistant, the Home Assistant mobile app on Android, and a WireGuard VPN to your place.

For level 1, allow half a day once port forwarding is under control (estimate). Levels 2 and 3 take several days of fine-tuning, tests included.

Security principles

  • No secret in clear text on the server. The server sees the ID, the name (for the notification), the address and the time. Never the password.
  • Three anchors frozen in the exe: the RustDesk server key, your technician public key, and the fingerprint of the receiver's TLS certificate. No certificate authority, no proxy.
  • A human validates. A received record replaces nothing until you validate, even for an already known client.
  • A single possible order at the client's: uninstall. It is signed with your PC's private key; the server carries it without being able to forge or alter one.
  • Least privilege. Each service has its own user and sees only what it needs. Only two small services run as root, with no open port.
  • Every risky change is reversible: database copy before any deletion, automatic rollback for the firewall, tests on an isolated instance before production.

Level 1The RustDesk server

The machine

Create a dedicated Debian 12 VM. With Proxmox, the Debian cloud image and cloud-init give a VM ready at first boot: administrator account with SSH key only, automatic updates, Docker. With another host, install Debian by hand and then Docker following the official documentation.

Then install: nftables, unattended-upgrades, qemu-guest-agent (under Proxmox) and Docker with the Compose plugin. Cockpit is a convenience for running commands from a browser, not a requirement.

RustDesk in Docker

Two containers: hbbs (directory) and hbbr (relay). The -k _ option forces them to refuse any client that does not present the server's key: without it, anyone could register.

Back up now

Copy data/id_ed25519 (the server's private key) into your password manager. If you lose it, every installed client will have to be reconfigured. Once the set-up is validated, replace latest with a specific version number so that updates remain under your control.

Ports and the router

PortUseTo forward
TCP 21115NAT type testYes

If you have two routers in series (the operator's box, then your own router), forwarding is done on each: box to router, router to the VM. Test from outside, for example with a phone on 4G. For TCP ports, Test-NetConnection <PUBLIC_ADDRESS> -Port 21116 from a PC away from home. UDP cannot be tested this way: the real test is a RustDesk session between two different networks.

The VM's firewall

Default policy: everything is refused inbound. RustDesk is open to the Internet. SSH and Cockpit answer only to the local network and the VPN. Outbound, the VM reaches the gateway (DNS) and the Internet, but no other device on your network: if the server were compromised, it could not pivot to your machines. IPv6 is disabled, because systemd-networkd re-enables it at each boot and a simple sysctl setting does not hold.

To apply a firewall rule remotely without risking locking yourself out, schedule a rollback before applying, then cancel it once everything answers. This is a pattern to adapt to your system.

Have this file loaded at boot (for example with a line include "/etc/nftables.d/*.nft" in /etc/nftables.conf and systemctl enable nftables), then check after a VM reboot that the rules are there.

Level 1The installer exe

The client must not configure anything. A Windows launcher embeds the installation script and the frozen values (server, key). The client double-clicks and answers two questions: their name, and a permanent password (Enter to generate one).

How it is built

  • A small C# program compiled with the compiler shipped with Windows (csc.exe, C# 5): nothing to install. It carries a requireAdministrator manifest.
  • It embeds a PowerShell script that installs RustDesk silently, installs and starts the service, applies the server and the key, sets the password, then checks the result.
  • It refuses to install a RustDesk installer whose Authenticode signature is not valid.
  • The password must be at least 12 characters, without spaces.
  • It writes a start-up log to %TEMP%\…Setup.log (options, rights, exit code, never the secret values). No log after a double-click means the exe did not start: SmartScreen or antivirus.
  • Before any installation, it can display installation terms that the client must accept (see "Terms and proof of acceptance"). Without acceptance, nothing is installed.
  • Options: /silent (no question, for scripted deployment; requires /accept if a text is embedded), /accept, /save, -Uninstall (complete uninstallation, see "Uninstalling a client").
  • At level 3, after sending the record, it waits for the technician's validation and then closes by itself (see "Closing the client's window on validation").
  • At level 3, with accepted terms, it also installs the maintenance task (see "Uninstalling a client"). -NoAgent at build time does without it.

Level 2Encrypted address book on your PC

This level removes note-taking. The exe encrypts the password with your public key, writes the record to the USB key, and a tool on your PC reads it.

Your technician key

Pg20-Technicien-Configurer.ps1 creates an RSA-2048 key pair. The private key stays in %APPDATA%\…\technician.key, protected by your Windows account (DPAPI). The public key, technician.pub.xml, is built into the exes. It is passed to Pg20-Exe-Compiler.ps1 with -TechnicianPublicKey.

The backup is mandatory

DPAPI ties the key to your Windows profile. A reinstalled Windows or a lost profile makes all the records unreadable, unless you have the backup.

The record format

A classic hybrid encryption scheme, with authentication:

  1. The exe randomly draws an AES-256 key and an HMAC key (64 bytes in total).
  2. These two keys are encrypted with your public key (RSA-OAEP).
  3. The record (name, computer, ID, password) is encrypted in AES-256-CBC with a random 16-byte IV.
  4. An HMAC-SHA256 protects the whole. Your PC verifies the HMAC before decrypting, and discards any record that was modified or made for another key.

The technician's tool

  • A local web page served on 127.0.0.1 only, with a random token per session, a Host header check and a CSP policy. The page never receives passwords. It stops by itself after 45 min of inactivity.
  • One-click connection: the rustdesk://connection/new/<ID>?password=… link opens RustDesk with the ID and password already filled in.
  • A small "Connect" window (WinForms), with keyboard search, shows only validated clients. It also carries the "Uninstall…" and "Delete…" buttons.
  • Two desktop icons (the quick window and the full page), launched without a console.
  • A scheduled watcher task with your rights, without a window (conhost --headless), a single instance. It reads the USB key, fetches the records from the server, applies the phone validations, and shows a Windows balloon for each new record. Its log never contains a password.
  • A shared lock (mutex) protects the address book: the page and the watcher can work at the same time without overwriting each other.

With this level, the fallback is the USB key: plugged into your PC, it is imported by itself, and new computers show as "To validate".

Level 3Direct sending and phone

The record goes straight from the exe to your server, without a USB key. A notification arrives on your phone and you validate with one button. This is the most convenient level and the only one that exposes home-made code to the Internet.

The principle, server side

The RustDesk server does not say when a computer registered. A small exporter therefore reads the hbbs SQLite database every 15 seconds, keeps a fingerprint (uuid, key, address) of each computer, and notes the moment it changes. This date serves as proof: a record is accepted only from a computer that has just installed itself.

ServiceUserWhat it does
Exporterroot, 15 s timerWrites peers.json and registrations.json, read-only for the others
Receiverpg20-inbox, systemd sandboxListens over TLS on 21120, validates, picks the code, drops the encrypted record in a waiting folder, keeps open the requests waiting for validation, serves the uninstall orders and receives their acknowledgements
Feedunprivileged, Bearer tokenServes the list of computers, the records and the validations to the local network and the VPN, drops the validation marker for the waiting exe, receives the signed orders
Forget serviceroot, triggered by a fileDeletes a computer from the database (see below)

The receiver's rules

  • TLS 1.2 minimum, with a self-signed certificate whose fingerprint is frozen in the exe: the exe sends only to that certificate.
  • Strict JSON, 4 KB at most, encrypted record of 100 to 3,000 base64 characters, numeric ID.
  • The computer must be registered on hbbs with the same public address as the request, less than 30 minutes ago.
  • 12 requests per 10 minutes per address, 100 per hour in total, 50 records waiting at most, purge after 14 days.
  • Identical answer (409) for any unknown computer: the service does not reveal which IDs exist.
  • The server draws the 4-digit control code and returns it to the exe, which displays it at the client's. A fake record gets a code that appears on no client's screen.

Closing the client's window on validation

At the end of the installation, the exe's window stays open until you validate, then closes by itself. The exe does not poll the server every few seconds: it makes a single request, which the server keeps open.

  1. With the control code, the receiver returns a random tracking number (32 hexadecimal characters), known only to the exe that has just sent the record. It stores it for 15 minutes in track/<tracking>.json, with the ID and the reception time.
  2. The exe sends POST /v1/wait with this number. The server keeps the request open for 20 seconds at most and answers as soon as the validation arrives. Otherwise it answers "not yet", and the exe renews the request, for 10 minutes at most.
  3. On POST /records/validate (called by Home Assistant, or by your PC when you validate in its address book), the feed drops track/<tracking>.ok next to the tracking file of the same record (same ID and same reception time). The receiver sees this marker within half a second.
  4. The exe displays "Validated by the technician", waits 3 seconds and closes. It exits with code 10, which the C# launcher recognises in order not to ask for a key press.

Safeguards: an unknown or expired number immediately gets the same 409 answer, so it cannot hold any connection. At most 8 waits are open at the same time, 2 per address (503 beyond that), and each address is limited to 40 requests per 10 minutes. After 10 minutes, or if the server is unreachable, the exe goes back to its usual behaviour: a message, then a key to press. Closing the window by hand during the wait has no consequence, since everything is already installed and sent.

The wait is limited to 20 seconds per request because some firewalls and routers cut a silent connection after 30 to 60 seconds: the exe renews it, which makes three requests per minute at most. For the feed (user nobody) to be able to drop its marker in the receiver's folder, its systemd unit gives it the receiver's group (SupplementaryGroups=pg20-inbox).

Installation on the VM

In this order: the feed first (it creates the token), then the receiver, then the forget service. The install scripts are idempotent.

Then open port 21120 in the VM's firewall, and forward TCP 21120 on the router box and your router. The feed's port 8099 stays reserved to the local network and the VPN.

If the certificate changes

A rebuilt VM regenerates the certificate, hence the fingerprint. All the exes already distributed will no longer be able to send a record until you rebuild them.

Home Assistant

Home Assistant acts as a bridge to the phone. It polls the VM's feed every 30 seconds, notifies, and relays the Validate button. The VM itself has no access to Home Assistant. The notification texts and aliases in the samples below are left in French, as in the kit's files: translate them to taste.

1. The secret. In secrets.yaml, the value contains the word "Bearer" followed by the token read with sudo cat /etc/pg20/feed.token on the VM:

2. The sensor. In configuration.yaml (or your REST sensors file). The feed adds pending_label, pending_code and pending_since to the computers whose record is waiting. Neither the password nor the encrypted record goes through it.

3. The validation command. REST commands can only be declared in YAML, and are not reloaded on the fly: restart Home Assistant after adding it. This is the only manual addition in the whole configuration, the rest is created in the interface.

4. The notification. A new record triggers a notification with the name, the ID and the code. Tapping the notification opens the validation page. The action button carries the record's ID and time, so that the validation applies only to that exact record.

5. The notification button. The mobile app sends back the mobile_app_notification_action event. The condition checks the exact format of the action before calling the server.

6. The validation page. Two scripts and a dashboard. The first validates the most recent waiting record and closes its notification. The second calls it then sends the phone back to its home screen.

The phone

  • Access to Home Assistant away from home: a WireGuard tunnel to your network, as a split tunnel per app (only the Home Assistant app goes through it, the rest of the phone goes out normally), with only your local subnet in the allowed addresses. Enable "Always-on VPN" in Android's VPN settings, otherwise the button will answer "validation not sent" at the client's.
  • The buttons of an Android notification appear only once the notification is expanded. This is why tapping the notification opens the validation page, with its big button.
  • Return to the home screen: the command_activity command asks Android for the "Appear on top" permission for the Home Assistant app. The launcher's package depends on your phone: adapt it in the script.
  • A new notification with the same tag replaces the previous one without an alert: there is one tag per computer ID.

Terms and proof of acceptance

Installing permanent access at someone's place without them having read it is a bad idea, legally and humanly. The exe can therefore display a text before installing anything, and keep the proof that the client accepted it. The text is yours: the repository provides only a template (conditions\conditions-modele.txt, in French, with a courtesy translation conditions-modele.en.txt), to be completed and reviewed by a professional in your country.

  1. You complete the text. Copy the template as conditions\conditions-YYYY-MM-DD.txt and fill in the fields in square brackets (technician, address, e-mail, retention period, erasure delay). The first line, Version : …, identifies the version. Keep every version a client has accepted: it is the one their proof designates.
  2. The build refuses an incomplete text. As long as a field in square brackets remains, Pg20-Exe-Compiler.ps1 stops.
  3. At launch, the exe displays the text: the client ticks "I have read…" and types their name (3 characters at least). Refusing or closing the window: nothing is installed (exit code 20). In silent mode, the /accept option is mandatory (code 21 otherwise) and the proof records "accepted by parameter": this is then a statement by the technician, not by the client.
  4. The proof travels in the encrypted record: PC time (UTC), typed name, name of the PC and of the Windows user, RustDesk ID, version of the text, SHA-256 fingerprint of the text, mode (window or parameter), seconds spent in the window. The server adds its own reception time, which does not depend on the client's clock. On the USB key, a separate file (rustdesk-consents.csv) plays the same role. The client keeps a copy of the accepted text in C:\ProgramData\Pg20-Info\.
  5. On your PC, the proof is stored with the client. On validation, the tool writes a file Documents\Pg20-Info-Preuves\Preuve-<ID>-<date>.txt ("Preuve" means proof), with the accepted text found by its fingerprint in the conditions\ folder. These files survive the deletion of the client.
What the proof is, and is not

It is a log kept by your tool: it shows who accepted which text, when and from which computer. It is not an electronic signature and does not replace a written agreement. The template provided is not legal advice and has not been reviewed by a lawyer.

Uninstalling a client

Uninstalling RustDesk at a client's means removing the service, the program, the firewall rules and above all the configuration that RustDesk leaves behind: its ID and its keys. Without that, a reinstallation gets the same identity back and the server sees no new registration (see the limits). The Uninstall-RustDeskFully function of Pg20-Client-Installation.ps1 does all of this, checks at the end that nothing remains and writes a log in C:\ProgramData\Pg20-Info\. It can check the computer's ID before acting (-ExpectedId: it stops without touching anything on another computer) and simulate without erasing anything (-DryRun).

The "Uninstall…" button of the "Connect" window asks you to type the client's name, then chooses the method by itself.

Computer with the maintenance task: fully automatic

  1. You click and type the client's name. Your PC signs an order "uninstall computer <ID>" with your private key and drops it on the feed (POST /orders).
  2. The client's computer reads the orders at start-up then every 30 minutes (scheduled task, system account, no window). It asks the receiver GET /v1/order?id=<its ID>.
  3. It verifies the order before anything else: signature (with the public key received at installation), action "uninstall", ID identical to its own, not expired, not dated in the future, not older than the installation of the task (anti-replay). Otherwise it does nothing.
  4. It uninstalls (same function as above, which re-checks the ID), informs the server (POST /v1/order-done), then deletes its own task and folder. If the network is down at that moment, it keeps a marker and retries at each run.
  5. Your PC sees the acknowledgement at its next synchronisation, removes the client from the list, the USB key and the server, and shows a Windows balloon. The client had nothing to do or see.

You can cancel as long as the computer has not executed the order (the same button offers it, and so does the page). An order never executed is forgotten after 30 days, and deleting the client or receiving a new record for its ID cancels the pending order. To avoid waiting 30 minutes: on the computer, Task Scheduler, Pg20-Info-Maintenance, Run.

The signed order

The same RSA key pair is used to decrypt the records and to sign the orders. The signed text starts with a prefix that separates these two uses. Dates are in UTC, and the computer reads the server's time (Date header) rather than its own clock, which may be wrong.

RouteWhereRole
GET /v1/order?id=receiver, InternetServes the computer's signed order. 404 if there is none, if it is expired or already executed. 60 requests per 10 minutes per address
POST /v1/order-donereceiver, InternetThe computer's acknowledgement (256 bytes at most). It never deletes the order: a fake acknowledgement cannot cancel anything
POST /orders, GET /orders, POST /orders/ackfeed, local network and VPN, tokenDropping an order (50 at most, one per ID), status (executed or not), deletion

The server can neither forge nor alter an order: it does not have the private key. It only carries.

Computer without the task: guided procedure

A computer installed with an older version of the exe does not have the task. The same button then prepares a self-contained command (the uninstall script, compressed in base64, on one line) and puts it in the clipboard; it opens the RustDesk session, and a guide tells you to paste it in an administrator PowerShell at the client's. The session drops about ten seconds after the start, the uninstallation continues on the computer, then "It's done" removes the client from the list. For this computer to get the task, run the recent exe on it again.

Deleting a client

Deleting a client in the tool makes it disappear everywhere, as if it had "never existed". Order of operations: the PC asks the server first, and if the server does not answer, nothing is deleted.

  1. The PC calls the feed (POST /peers/forget, with the token).
  2. It removes the client from its list (name, computer, password) and its lines from the plugged-in USB key.
  3. On the VM, the feed drops the request in a waiting folder. A systemd .path unit immediately starts the forget service, which copies the database, deletes the computer's row, then restarts hbbs once.

Safeguards of the forget service: ordinary files of 1 KB at most, no symbolic link, numeric ID of 6 to 12 digits, 10 computers at most per run, 20 pending requests at most, every file read is deleted. The PC keeps only a minimal trace (ID and time) so that an old line from another copy of the key does not resurrect the client.

Uninstall at the client's first

If RustDesk is still installed there, it registers again by itself and the client comes back as "To validate". Uninstall it before deleting. With the maintenance task, the "Uninstall…" button does both in the right order.

By hand, on the VM: sudo pg20-forget-peer <ID> (database copy, "yes" confirmation, hbbs restart). This script is also used to allow a reinstallation on an already known PC, see the limits.

Checklist to validate your own setup

  • After a VM reboot: the containers, the firewall and the services come back by themselves.
  • From outside: the open ports answer, ports 22, 9090 and 8099 stay closed.
  • A client without the server key is refused by hbbs.
  • A record with a wrong code or an unknown computer is refused (answer 409).
  • An exe pointing to a wrong TLS fingerprint sends nothing.
  • The Validate button fails cleanly, with a message, when the phone's VPN is off.
  • The forget service does make a database copy before deleting.

Known limits

  • Reinstalling RustDesk on the same PC. RustDesk keeps its keys, so hbbs sees no new registration and the receiver refuses the record, which stays on the USB key. To send it anyway: sudo pg20-forget-peer <ID> on the VM, let the computer register again (less than a minute), run the exe again. A PC never equipped does not have this problem.
  • Home Assistant or the sensor down: a record that arrived during that time is not notified. It appears as "To validate" in the PC tool.
  • The technician's PC must be on and reach the server (local network or VPN) to fetch the records. Otherwise they wait, encrypted, 14 days on the server.
  • The sensor reads only the 30 most recent computers.
  • Automatic closing of the client's window: only the validation of a record that arrived from the server triggers it, not that of a client imported from the USB key. Validating from the PC does not close the phone's notification. Without validation, the window waits 10 minutes at most.
  • No "online" indicator: hbbs does not publish this information.
  • A single technician and a single key.
  • A regenerated TLS certificate forces you to rebuild the exes.
  • Automatic uninstallation is not instantaneous: the computer polls the server every 30 minutes, or at its next start-up if it was off. It works only on computers installed with the maintenance task; the others go through the guided procedure.
  • A compromised server could replay an order that was already signed and then cancelled for a computer (effect: uninstalling RustDesk). Orders are valid for 30 days.
  • The terms text is a template: to be completed and reviewed. The screens of the exe and of the scripts are in French.

Maintenance

  • Backups: the server's private key (data/id_ed25519), the database data/db_v2.sqlite3, the technician's private key, and the feed token.
  • Updates: unattended-upgrades for the system. For Docker images, a chosen manual update is better than an unchecked latest.
  • Regular review: re-read the firewall, the list of computers on the server, and delete the clients whose agreement you no longer have.

Alternatives

This project answers a specific need: a lone technician who wants to keep control of their data and pay no subscription. Depending on your situation, another route may be wiser.

  • Stop at level 1 or 2. You keep a server of your own and the encryption of the passwords, without exposing home-made code.
  • RustDesk Server Pro: the publisher offers a paid version with a management console and address book. Check its current offer and terms before deciding.
  • MeshCentral or a commercial monitoring tool: more complete, with online status and fleet management, at the price of a heavier installation or a subscription.
